# Production account rollout

PostgreSQL owns stable account UUIDs, login names, credentials, active status, incident assignments, and account audit events. The role matrix is fixed. Administrators manage accounts, integrations and all incidents. Coordinators manage assigned incidents, including rooms, invitations and alerts. Responders participate in assigned incidents. QR guests retain their temporary room-only session and current guest permissions. Unknown or inactive memberships deny access.

1. Add backward-compatible schema and explicit, transactional namespace CLI bootstrap and legacy import. Bind legacy factors only to the exact configured operator identity and revoke old operator sessions on activation. Lock bootstrap and account changes to protect the last active administrator.
2. Carry verified account UUIDs through login and MFA. Require individual factor enrollment and bind challenges to account and credential generation. Reuse password hashing, WebAuthn verification, encrypted TOTP and one-use recovery codes. Issue temporary credentials only through an authenticated administrator workflow and require replacement before protected access.
3. Gate every server action and route using central account and incident capabilities. Inventory reads and writes for media tokens, XMPP grants, boards, documents, chat, transcript, assistant, invites and alerts. Recheck capability on fresh tokens and XMPP reconciliation. Measure active stream revocation separately from HTTP denial.
4. Add independent tests with legacy upgrade, account role/assignment changes, disabling, duplicate bootstrap, recovery and last-administrator concurrency. Rehearse restore before activation. Keep old and new schema compatible until the cutover. After activation, rolling back to an old binary would bypass account enforcement, so keep ingress closed until a compatible version is ready or recover the pre-activation snapshot in isolation.
5. Stage on private HTTPS with durable PostgreSQL and archive storage and persistent TLS/MFA keys. Verify two-host media and chat, backups and failover independently before accepting the production deployment. Keep synthetic exercise accounts in their existing isolated mode.

## Isolated staging

Build one image digest using the root Dockerfile. Create a new namespace, provision persistent PostgreSQL and restore a verified backup if upgrading. Keep exercise databases separate. Apply the migration job using the same image digest, then run `node scripts/bootstrap-admin.mjs new LOGIN` with the password on stdin in a namespace-controlled pod with DATABASE_URL from the runtime Secret. For an upgrade, run `node scripts/bootstrap-admin.mjs legacy LOGIN` with the original operator and hash, the unchanged MFA key, and the exact same canonical HTTPS origin for passkeys. Never put the password in command arguments, YAML, or Git.

Set RESPONSEABLE_ACCOUNTS_ENABLED=true and RESPONSEABLE_MFA_KEY in the runtime Secret. Disable ingress during activation and ensure all old web replicas are gone before reopening it. Keep a verified pre-activation backup. Restore and validate in isolation if reverting to a version that lacks account enforcement. The new session hash namespace prevents old replicas from accepting a role-scoped session, but old routes still permit the configured legacy login if left reachable.

For XMPP, start with native PostgreSQL chat for unmapped rooms. Use the private ejabberd administrative channel to create persistent members-only rooms before inserting an explicit xmpp_rooms mapping. A mapped room uses Converse and PostgreSQL MAM for writes and historical chat, with separate backups of the archive and room metadata. Keep the XMPP admin listener private. Existing LiveKit connections require eviction or disconnect on membership changes. The short join grant alone does not terminate active media.

An ingress that supplies RESPONSEABLE_TRUSTED_CLIENT_IP_HEADER must overwrite that header and deny direct pod access. The password route rate limits by login and trusted client IP, or by login with an unidentified source bucket when no verified address is available. Apply ingress rate limiting to bound traffic across many usernames.

SMS in account mode requires RESPONSEABLE_INVITE_KEY. For an existing instance, copy the effective previous signer into that dedicated Secret before cutover so pending previews and already issued links remain consistent. If intentionally rotating the signer, expire pending SMS drafts and their inactive invites before enabling SMS. Store the signer separately from account password hashes.
